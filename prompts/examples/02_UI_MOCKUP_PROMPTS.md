# 02 — Промпты для макетов Admin UI (дизайн)

> Контекст: держать `00_OVERVIEW_AND_CONTRACTS.md`. Эти промпты — для **проектирования макетов**
> (визуал/структура экранов), без реализации. Реализация — в `03_FRONTEND_PROMPTS.md`.
> Назначение Admin UI (HLD §3.4.2): тонкий web-интерфейс поверх Admin API Policy Engine для управления
> `application_profiles`, `service_class`, `workload_form`, `rate_limit_tier`/policy cap, версиями политик и rollback,
> просмотра audit log и read-only статуса. **Дашборды/метрики остаются в Grafana/Langfuse** — UI их не дублирует,
> только даёт лёгкий статус-обзор и ссылки.
>
> Дизайн-принципы: интерфейс для платформенной команды (плотный, информационный, не маркетинговый);
> RBAC-aware (viewer/editor/admin — разный набор действий); безопасные дефолты (опасные действия —
> подтверждение + видимый аудит-след). Светлая/тёмная тема. Без эмодзи в проде.

---

## Промпт 1 — App Shell / Layout

> Спроектируй каркас приложения Admin UI.
>
> Layout: левый сайдбар-навигация + топбар (текущий пользователь, роль-бейдж, окружение-бейдж
> `DEV/STAGE/PROD`, индикатор версии активного policy-снапшота, переключатель темы, logout).
>
> Навигация (пункты, видимость зависит от роли):
> 1. **Status** — read-only обзор системы (Промпт 3)
> 2. **Application Profiles** — CRUD профилей (Промпт 4)
> 3. **Identity Mappings** — связки ключ→application (Промпт 5)
> 4. **Policies / Rules** — правила классификации + редактор (Промпт 6)
> 5. **Policy Versions** — версии и rollback (Промпт 7)
> 6. **Rate Limit Tiers** — тиры лимитов (Промпт 8)
> 7. **Audit Log** — журнал изменений (Промпт 9)
> 8. **Service Classes** — справочник (read-only, Промпт 10)
>
> Состояния роли: `viewer` видит всё, но кнопки мутаций скрыты/disabled с тултипом «нужна роль editor/admin»;
> `editor` — CRUD профилей/маппингов/политик; `admin` — плюс rate-tiers и rollback.
>
> Покажи: как выглядит активный пункт, как отображается роль, как показывается «снапшот vN, обновлён N сек назад»
> (зелёный — свежий, жёлтый — stale). Подумай: что важнее всегда видеть в топбаре — окружение или версию снапшота?
> Для prod-среды бейдж окружения должен быть заметным (предохранитель от случайных правок в проде).

## Промпт 2 — Login / Auth (Keycloak + dev-admin)

> Спроектируй экран входа `/login`.
>
> Основной путь — **«Войти через Keycloak»** (OIDC redirect): крупная primary-кнопка, краткое пояснение
> «корпоративная учётная запись». После возврата с токеном — редирект на сохранённый `returnTo` или на Status.
>
> Опциональный блок **Dev admin** — показывается **только** когда сервер сообщил `DEV_ADMIN_ENABLED=true`
> (флаг приходит с бэка). Это форма username+password со ВИДИМЫМ предупреждением «Только для сред разработки.
> Не для prod.» и жёлтой рамкой. В prod-сборке блок отсутствует полностью.
>
> Состояния: загрузка (проверка флага/сессии), ошибка OIDC (истёкший код, отказ), ошибка dev-login
> (неверные креды). Подумай: dev-admin не должен выглядеть как равнозначная альтернатива — это «аварийная»
> опция, визуально вторичная и явно помеченная небезопасной для прода.

## Промпт 3 — Status (read-only обзор)

> Спроектируй стартовый экран `/status` — лёгкий операционный обзор (НЕ замена Grafana).
>
> Содержит:
> - Полоска состояния backend: Policy Engine (up/ready), Priority Queue (up/ready), Redis, PostgreSQL,
>   версия активного снапшота и время последней публикации.
> - 4 компактные карточки по очередям (CRITICAL/HIGH/STANDARD/BATCH): текущая глубина (`queue_depth`) и
>   max wait time vs порог Starvation Guard (зелёный/жёлтый/красный индикатор). Это read-only «здесь и сейчас».
> - Текущий `shedding_level` (Normal/Yellow/Orange/Red/Black) с цветом и avg GPU utilization.
> - Кнопки-ссылки «Открыть в Grafana» и «Открыть в Langfuse» (внешние, для детального разбора).
>
> Подумай: что показать крупно — общее здоровье или ближайшую проблему? Скорее проблема: если какой-то класс
> приближается к порогу starvation или shedding ≥ Orange, это должно бросаться в глаза. Без интерактивных
> графиков — только текущие значения + пороги; за историей пользователь уходит в Grafana.

## Промпт 4 — Application Profiles (list + detail/edit)

> Спроектируй раздел `/profiles`.
>
> **Список:** таблица профилей с колонками: `application_id`, `scenario`, `service_class` (цветной бейдж),
> `workload_form`, `model`, `rate_limit_tier`, `enabled`. Фильтры: по application_id, service_class, scenario,
> enabled; поиск `q`; пагинация. Действие «Создать профиль» (editor+).
>
> **Detail/Edit** (`/profiles/:profileId`): форма со всеми полями профиля —
> `application_id`, `scenario`, `allowed_api_types` (мультиселект chat/embedding/function_call/batch),
> `service_class` (select 4 значения), `workload_form` (select 4 значения), `model`,
> `rate_limit_tier` (select из существующих тиров или none), `policy_cap` (структурированный JSON-редактор),
> `limits` (max_tokens и т.п.), `enabled` (toggle).
>
> Важно показать визуально: **изменение `service_class` или `workload_form`** — это влияющее на трафик действие;
> при сохранении показать диалог-подтверждение «это изменит классификацию для application_id=… и опубликует новый
> снапшот vN+1», с указанием, на какие identity_mappings это повлияет.
>
> Подумай: один `application_id` имеет много профилей под разные сценарии (суфлёр realtime → CRITICAL,
> пост-анализ → HIGH). Список должен легко это показывать (группировка/сортировка по application_id).
> Что важнее на detail — текущие значения или предупреждение о последствиях? Для service_class — последствия.

## Промпт 5 — Identity Mappings

> Спроектируй раздел `/identity-mappings`.
>
> **Список:** таблица: `key_fingerprint` (усечённый, с copy), `application_id`, `scenario`, привязанный
> `profile_id` (ссылка на профиль), `tuz`, `enabled`. Фильтры по application_id/enabled, поиск.
>
> **Create/Edit:** форма: `key_fingerprint` (вставляется hash/fingerprint — НЕ plaintext key; подсказка
> «система не хранит сам ключ»), `application_id`, `scenario`, выбор `profile_id` (из существующих),
> `tuz` (опц.), `enabled`. Валидация: выбранный профиль должен соответствовать application_id/scenario.
>
> Подумай: это место, где «ключ → права». Нужно явно подчёркивать, что `X-Application-ID` из запроса
> НЕ переопределяет маппинг (можно показать инфо-блок про доверенную identity). Опасное действие — отвязать/
> отключить маппинг (ключ перестанет резолвиться) → подтверждение.

## Промпт 6 — Policies / Rules (редактор правил классификации)

> Спроектируй раздел `/policies`.
>
> **Список политик:** name, kind (`classification`), enabled, current_version, обновлено. Действие «Создать».
>
> **Редактор** (`/policies/:id`): двухпанельный.
> - Слева — **YAML-редактор** правил (chain-of-responsibility): подсветка синтаксиса, номера строк.
>   Правило = `priority` + `when` (application_id/api_type/scenario/контекст) + `set` (service_class/workload_form/...).
> - Справа — **панель валидации/предпросмотра**: кнопка «Validate» вызывает dry-run (`POST /policies/{id}/validate`),
>   показывает ошибки парсинга и **результат прогона golden-векторов классификации** (какие входы → какой
>   service_class), чтобы видеть эффект до сохранения.
> - Внизу — «тест-инпут»: ввести application_id/api_type/scenario → показать вычисленный ClassificationResult.
>
> Сохранение (editor+) требует поле `reason` (для audit/версии) и предупреждает «создаст version N+1 и новый снапшот».
>
> Подумай: главный риск — сломать классификацию. Поэтому Validate/preview должен быть всегда на виду, а Save —
> только после успешной валидации. Что важнее — свобода редактирования YAML или защита от ошибки? Защита:
> блокируй Save при ошибках парсинга.

---

## Промпт 7 — Policy Versions + Diff + Rollback

> Спроектируй экран версий `/policies/:id/versions`.
>
> Содержит: таблицу версий (version, author, role, reason, created_at, checksum, бейдж «current»).
> Выбор двух версий → **unified diff** YAML (`/policies/{id}/diff?from=&to=`). Действие **Rollback к версии**
> (только admin): открывает подтверждение «откат создаст НОВУЮ версию N+1 с телом версии K, история сохранится»,
> требует `reason`, показывает кого это затронет, после успеха — тост + обновление списка + индикатор нового снапшота.
>
> Подумай: rollback не должен выглядеть как «удаление» — это forward-only операция (новая версия). Историю
> нельзя терять. Diff — основной инструмент принятия решения, он должен быть крупным и читаемым.

---

## Промпт 8 — Rate Limit Tiers

> Спроектируй раздел `/rate-limit-tiers` (admin).
>
> Таблица тиров: `tier` (напр. `coding_agent`), `rps_per_key`, `burst`, description, сколько профилей используют.
> Create/Edit: tier name, rps_per_key, burst, description. Удаление запрещено/предупреждается, если тир используется
> профилями (показать список профилей-потребителей).
>
> Контекст для дизайна: тир ограничивает per-key RPS поверх базового service_class (напр. coding-agents 10 RPS/ключ,
> чтобы не вытеснять другие HIGH). Покажи это пояснением рядом с формой.

## Промпт 9 — Audit Log Viewer

> Спроектируй раздел `/audit`.
>
> Таблица событий (из `audit_log`): timestamp, actor (для admin-событий) или application_id, action
> (`policy_change`/`dispatch`/`reject`/`priority_elevation`/`overload`/`stream_*`), service_class, status,
> `trace_id` (copy + ссылка в Langfuse), policy_version. Для policy-событий — раскрытие с old/new version,
> change_id, reason, rollback_result.
>
> Фильтры: actor_id, action, trace_id, application_id, период (from/to), service_class. Пагинация.
> Детальная панель события (drawer): полный JSON безопасных полей (без plaintext prompt — только content_hash),
> latency_breakdown, признак подписи HMAC (verified).
>
> Подумай: аудит — это про «кто/что/когда изменил» и «почему отклонили/повысили». Самые частые сценарии —
> найти по trace_id (инцидент) и посмотреть историю изменений конкретного профиля/политики. Оптимизируй фильтры
> под это. Никогда не показывай plaintext prompt — только хэши/идентификаторы.

---

## Промпт 10 — Service Classes (справочник, read-only)

> Спроектируй read-only справочник `/service-classes`.
>
> Карточки/таблица 4 классов с параметрами из контракта: DRR-вес, min GPU доля, целевые SLA queue-wait
> (p95/p99), порог Starvation Guard, rate limit (burst/sustained), поведение на стадиях shedding (Yellow/Orange/Red).
> Плюс краткое пояснение разницы `service_class` vs `workload_form`. Это справочная страница для онбординга
> платформенной команды — без действий, только структурированная информация из `00`.

---

## Сквозные элементы (для всех экранов)
> - **Snapshot indicator**: после любой мутации показывать «снапшот обновлён → vN+1» (toast + топбар).
> - **Confirm-диалоги** для влияющих на трафик действий (смена service_class/workload_form, отключение маппинга, rollback) с явным указанием последствий и обязательным `reason` где это пишется в audit.
> - **Empty/Loading/Error** состояния для каждой таблицы и формы.
> - **RBAC-gating**: кнопки мутаций скрыты/disabled для недостаточной роли, с тултипом.
> - **PROD-guard**: в prod-окружении влияющие действия требуют дополнительного подтверждения (бейдж окружения красный).
