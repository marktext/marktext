# ТЗ: агентские комментарии в MarkText

Версия 1. Основание — согласованное описание от 2 октября 2026.

## 1. Назначение

Доработать редактор MarkText так, чтобы рецензия Markdown-документа комментариями запускала локальный агентский harness. Агент правит файлы репозитория и оставляет ответ в треде. Человек смотрит diff и ведёт git через встроенный терминал.

Редактор не выбирает поставщика модели и не подменяет harness. Модель берётся из списка, который уже настроен в выбранном harness.

## 2. Границы первой версии

В версии есть:

- одно окно на одну папку git-репозитория;
- комментарии к выделению в `.md` текущего файла;
- чат с выбранным harness;
- панель diff;
- встроенный терминал в корне репозитория.

В версии нет:

- живой работы нескольких людей, присутствия и учёток;
- автокоммита;
- принятия или отклонения отдельных кусков в панели diff;
- каталога моделей внутри редактора и прямого подключения к LiteLLM;
- отправки комментариев из других файлов одним действием;
- блокировки документа на время хода агента.

## 3. Harness

Из коробки поддерживаются три локальных процесса:

| Harness | Запуск по умолчанию |
|---|---|
| OpenCode | `opencode acp` |
| Pi | `pi-acp` |
| Cursor | `cursor-agent` |

Пути к программам задаются в настройках приложения. Если путь пуст, программа ищется в `PATH`. Редактор их не устанавливает и не поставляет.

OpenCode и Pi подключаются по Agent Client Protocol. Cursor подключается через CLI `cursor-agent` адаптером, который приводит поток сообщений, вызовы инструментов и запросы разрешений к тому же окну чата.

У каждого адаптера есть операция «список моделей»: модели, уже настроенные в этом harness, а не общий справочник редактора. Если harness не вернул ни одной модели, выбор недоступен и в настройках показывается причина. Редактор не предлагает ввести произвольный идентификатор модели вместо этого списка.

## 4. Настройки harness и модели

В настройках пользователь выбирает:

- harness;
- одну модель из списка, который вернул этот harness.

Пара «harness + модель» запоминается отдельно для каждого репозитория. Для нового репозитория подставляется последняя успешно использованная пара, если её модель всё ещё есть в списке.

Смена harness переключает чат на сессии этого harness. Смена модели не переписывает уже идущую сессию. Следующий новый чат этого harness стартует с новой моделью. Если пользователь меняет модель при открытой сессии, редактор сообщает, что текущая сессия останется на прежней модели, и предлагает открыть новый чат. Старая сессия сохраняется в списке.

Запросы разрешений harness (правка файлов, команды) показываются в чате. Ответ уходит обратно в harness. Своей политики разрешений у редактора нет.

## 5. Комментарии

### 5.1. Создание

Комментарий создаётся из выделения в открытом `.md`. Появляется подсветка в тексте и тред в боковом списке. Без выделения создать комментарий нельзя.

В треде человек может оставить несколько своих реплик до и после отправки агенту. Подпись человека берётся из `git config user.name`. Если имя не задано, подпись — `me`.

### 5.2. Состояния

У треда два состояния: неразобранный и закрытый. Закрыть или удалить тред может только человек. Ответ агента состояние не меняет.

Неразобранные видны сразу. Закрытые скрыты, пока пользователь их не включит.

### 5.3. Хранение и привязка

Текст `.md` комментариями не размечается. Треды лежат в репозитории, в каталоге `.marktext/comments/`, по одному JSON-файлу на исходный `.md`. Каталог обычный для git: редактор его не коммитит и не добавляет в `.gitignore`.

Привязка треда — цитата выделенного фрагмента и контекст вокруг неё. После внешней правки редактор ищет цитату заново. Если цитата нашлась однозначно, подсветка переезжает. Если нет, тред остаётся и помечается оторванным. Оторванный тред можно отправить агенту; в сообщении есть пометка, что цитата в файле не найдена.

Человек может править свои реплики после отправки. Уже отправленное сообщение в чате из-за этого не меняется.

### 5.4. Ответ агента

Помимо правок файлов агент пишет ответ в каждый тред, который был в отправленной пачке. Ответ — новая реплика в треде, автор — выбранные harness и модель. Тред остаётся неразобранным.

Агент не закрывает тред, не удаляет его и не меняет реплики человека. Запись ответа идёт через операцию редактора, а не прямой правкой JSON.

Полный ход по-прежнему виден в чате. Реплика в треде — ответ по этому комментарию, а не замена чата.

## 6. Отправка агенту

Две команды, обе только для текущего файла:

- отправить выбранный тред;
- отправить все неразобранные треды этого файла.

Выбранный тред — отмеченный в списке или подсветкой. Если ничего не выбрано, первая команда недоступна. Оторванные неразобранные треды входят во вторую команду.

В сообщение сессии входят путь файла, цитата, признак оторванности и все реплики человека в треде. Редактор требует от агента по каждому такому треду вызвать ответ в тред и не менять состояние треда.

Пока ход не закончен и не отменён, новые отправки недоступны. Ход можно отменить.

Чат двусторонний: произвольное сообщение пишется в ту же сессию, без комментария.

## 7. Сессии чата

Одна активная сессия на пару «репозиторий + harness». У пары есть список сессий. «Новый чат» создаёт сессию и не удаляет предыдущие. После перезапуска открывается последняя сессия этой пары.

Переписка хранится в данных приложения на машине пользователя, ключ — путь репозитория и harness. В git она не попадает.

Если harness умеет возобновлять свою сессию, редактор хранит её идентификатор и поднимает ту же сессию. Если нет, редактор показывает сохранённую переписку и начинает у harness новый процесс с этой историей в контексте, насколько протокол harness это позволяет.

## 8. Правки и diff

Агент сам записывает файлы репозитория. Документ в это время не блокируется, человек может править текст.

После хода открывается панель diff. В неё попадают пути, которые harness записал в этом ходе. Для них показывается `git diff` относительно `HEAD`. Если человек правил тот же файл, его правки входят в тот же diff.

Та же панель отдельно открывает полный diff рабочей копии. Панель только для просмотра: принять или отклонить кусок в ней нельзя. Откат делается в терминале.

Автокоммита нет. Коммит, ветка, откат и push выполняются во встроенном терминале. Текущий каталог терминала — корень репозитория.

## 9. Поведение без репозитория и без harness

Если открытая папка не является git-репозиторием, агентский режим выключен: нет отправки, чата, diff и терминала. Редактор сообщает, что нужна папка репозитория. Отдельного мастера `git init` нет.

Если исполняемый файл harness не найден или список моделей пуст, старт сессии недоступен, причина видна в настройках и при попытке отправить комментарий.

## 10. Сценарии приёмки

1. Открыть git-репозиторий с `.md`, выделить фрагмент, написать две свои реплики. В файле `.md` маркеров комментария нет, JSON треда есть в `.marktext/comments/`.
2. В настройках выбрать каждый из трёх harness и модель из его списка. Новый чат стартует с этой парой.
3. Отправить один выбранный тред. Агент меняет файлы репозитория и добавляет в этот тред свою реплику. Состояние треда остаётся неразобранным. Закрывает его человек.
4. Отправить все неразобранные треды текущего файла. Треды другого файла в сообщение не входят. На каждый тред пачки есть реплика агента.
5. Произвольное сообщение уходит в ту же сессию, что и комментарии. Переключение harness открывает его сессии. «Новый чат» оставляет старый в списке. После перезапуска открыта последняя.
6. Запрос разрешения harness появляется в чате, ответ возвращается harness. Ход отменяется кнопкой, во время хода отправка недоступна.
7. После хода панель показывает diff только записанных в этом ходе путей относительно `HEAD`. Полный diff рабочей копии открывается отдельно. Куски в панели не принимаются.
8. Коммит из терминала в корне репозитория создаёт коммит только когда его сделал человек. Сами по себе ни правки агента, ни комментарии не коммитятся.
9. После правки, уничтожившей цитату, тред помечен оторванным и всё ещё отправляется.
10. Папка без git не запускает агента.

## 11. Нефункциональные ограничения

Редактор не отправляет ключи LiteLLM и не хранит их. Ключи и базовый URL остаются в конфигурации harness.

Каталог комментариев пригоден для обычного git diff и merge. Конфликт JSON не склеивается специальным алгоритмом: это обычный конфликт файла, его разрешает человек.

Отмена хода останавливает текущий запрос к процессу harness. Уже записанные файлы не откатываются сами.
